# Sutra

Локальная CRM для партнёра сетевого бизнеса: косметика, БАД, бытовая химия — любой каталог. Телефон и карточки клиентов остаются на устройстве. Покупка сама собирает календарь касаний.

## Стек

Expo SDK 58, React Native, TypeScript, `expo-sqlite`, `expo-notifications`, Expo Router.

Это офлайн-первая база на одного человека. SQLite — источник правды. Каждая запись дополнительно кладётся в `sync_outbox`. Позже её можно отдать в Supabase своим воркером или заменить драйвер на PowerSync, не трогая планировщик.

Почему не другие варианты на старте:

- **Supabase как единственная база.** На кухне у клиента сети часто нет. Данные не должны уезжать в облако, пока синхронизацию не включили явно.
- **WatermelonDB.** Нужен, когда ленивые реактивные списки и свой синк окупают нативную настройку. Для сотен клиентов и тысяч задач хватает `expo-sqlite`.
- **Flutter и Drift.** Равный по качеству путь, если команда пишет на Dart. Здесь выбран Expo: генератор дат — обычный TypeScript, его проверяют тесты без эмулятора, а AAB для RuStore собирает EAS.

Название на телефоне — Sutra. Идентификатор пакета: `com.popov_ds.sutra` (одинаковый для обоих flavor). В Gradle два **product flavor**: `rustore` (РСЯ, биллинг RuStore) и `play` (Google Play, свой блок РСЯ). Канал попадает в JS через `APP_DISTRIBUTION` и `extra.distributionChannel` в `app.config.js`.

```bash
npx eas-cli@latest build -p android --profile rustore   # APK, RuStore
npx eas-cli@latest build -p android --profile play        # AAB, Google Play
```

Локальный release (Windows, как в YogaScheduler — отдельные папки по магазину):

```powershell
npm run build:rustore   # dist/rustore/Sutra-rustore-release.apk
npm run build:play      # dist/play/Sutra-play-release.aab
npm run build:play:apk  # dist/play/Sutra-play-release.apk (тест)
npm run build:all       # RuStore APK + Play AAB
```

Артефакты Gradle по-прежнему в `android/app/build/outputs/...`; в `dist/play` и `dist/rustore` скрипт копирует готовые файлы с понятными именами.

Скрипт подтянет Ninja 1.12 в `scripts/ninja/`. Dev-сборки: `npm run android:rustore` / `npm run android:play`. После `expo prebuild` снова пропишите release-подпись и `productFlavors` в `android/app/build.gradle` (см. `credentials/keystore.properties`).

## Как устроен код

```text
src/app            экраны Expo Router
src/domain         даты, схема 0-3-7-15, тексты задач. Без React и без SQLite
src/data           транзакции: покупка, статус, просрочка, outbox
src/db             схема и очередь доступа к файлу базы
src/notifications  утренний локальный план на 14 дней
src/sync           порт SyncAdapter, реализации пока нет
```

Запись в базу идёт через одну очередь. `expo-sqlite` включает в открытую транзакцию любой запрос, который стартовал, пока она не закрыта. Очередь не даёт экранам вклиниться между `BEGIN` и `COMMIT`.

## Касания

День покупки — календарный день `purchased_on`, не момент сохранения и не UTC.

При `recordPurchase` (`src/data/purchases.ts`) вызывается `buildPurchaseTasks` (`src/domain/touchPlan.ts`). В одной транзакции пишутся покупка и задачи:

| Когда | Задача | Метка |
| --- | --- | --- |
| день 0 | Сервис: как пользоваться, развести, хранить | Сервис |
| день 3 | Контроль самочувствия и вкуса | Сервис |
| день 7 | Промежуточный результат | Сервис |
| день 15 | Кросс-селл из каталога | Допродажи |
| за 4 дня до конца курса | Напомнить, что продукт заканчивается | Допродажи |

Курс длится `durationDays` суток с дня покупки. Расчётное окончание — `purchased_on + durationDays`, это первый день уже без продукта. Если курс короче 4 дней, напоминание о повторе встаёт в день покупки и не уезжает в прошлое. День 15 не отрезается коротким курсом: Детокс на 14 дней всё равно получает кросс-селл.

Пример. Сыворотка куплена 2 ноября 2026, срок использования 28 дней:

- 02.11 сервис, 05.11 контроль, 09.11 результат, 17.11 кросс-селл
- курс заканчивается 30.11, повтор — 26.11

Перевод в статус «Постоянный клиент» (именно смена, не создание карточки уже с этим статусом) ставит одну задачу «Окно партнерства» через 21 день. Повторный перевод в тот же день не дублирует её: у задачи есть `dedupe_key`.

Просрочка считается по календарю. Выполненная задача просроченной не становится.

## Утро

На Android и iOS приложение планирует локальное уведомление на 09:00 на ближайшие 14 дней, где есть невыполненные касания. В уведомлении план этого дня. Просроченные с прошлых дат остаются в блоке «Просрочено» на экране «Сегодня» и в утреннее пуш не смешиваются. В браузере уведомления не ставятся.

## Запуск

```bash
npm start
npm run web
npm test
npm run typecheck
```

Каталог продуктов пустой после установки — позиции добавляются в «Справочники → Продукты». На Android включено `allowBackup: false`, чтобы после переустановки не поднималась старая `partner-crm.db` из Google Drive.
